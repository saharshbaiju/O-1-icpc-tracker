Project Title: O(1) Lite — an ICPC practice tracker for college competitive-programming teams

3.1. Detailed description of the project

College teams preparing for the ICPC solve problems on Codeforces, follow practice problem lists, and usually track who solved what in a shared spreadsheet. That spreadsheet repeats every student's details and every problem's details on every row, so it is slow to update and easy to corrupt. O(1) Lite replaces it with a small relational database: students record their submissions, form ICPC teams of up to three, keep practice sheets for their team, and see a leaderboard and their progress on each sheet.

This is a deliberately compact design of nine tables, so that every table can be explained in a sentence and every normalisation step can be shown on real attributes.

Users

There is one kind of user, the student: they solve problems (submissions are recorded against them), belong to at most one team, and see the leaderboard and their team's sheet progress.

Why this needs a database, not just Codeforces API calls

Codeforces supplies only raw submissions for one handle at a time. Everything else the application shows either does not exist on Codeforces or needs data from many users at once:

  • Our own data: universities, teams, practice sheets and topic tags are created in O(1). There is no API to fetch them from; the database is their only home.
  • Queries across users: the leaderboard, a team's sheet progress, and "which sheet problems has nobody in the team solved" join and aggregate the submissions of many students. Through the API that is one call per student on every page load, and the API is rate-limited; in SQL it is one query over stored rows.
  • History and availability: submissions are synced once and stored, so pages work even when Codeforces is slow or down, and past data stays available.
  • Integrity: keys, foreign keys, CHECK constraints and a trigger guarantee that a team never has four members, a sheet never lists a problem twice, and a submission never points at a missing user. An API gives no such guarantees about our data.
  • Derived values without duplication: solved counts, ranks and progress are views computed from base tables, so they can never disagree with the submissions.

The Codeforces API is therefore only a data source for one table (Submission, via a sync job); the database is the system of record for everything.

What the system stores

  • University — name (unique) and city.
  • User — name, unique e-mail, password hash, optional Codeforces handle (unique), university, and the team they belong to (if any).
  • Team — an ICPC team with a unique name; at most three students.
  • Problem — identified by its Codeforces code (e.g. 1520C), with a title and a difficulty rating. Its URL and difficulty band (Easy / Medium / Hard) are derived from the code and the rating, so they are not stored.
  • Topic — Greedy, DP, Graphs, …; a problem can have many topics.
  • Submission — one attempt by a user at a problem at a particular moment, with a verdict and a language.
  • Sheet — a practice list belonging to one team, with an optional deadline, containing an ordered list of problems.

Business rules

  1. Every user studies at exactly one university.
  2. E-mail is unique; a Codeforces handle, if given, is unique.
  3. A student belongs to at most one team; a team has at most three members (enforced by a trigger).
  4. A problem is identified by its Codeforces code and may carry several topics.
  5. A submission is identified by who submitted, which problem and when. A user cannot submit the same problem twice in the same instant.
  6. A sheet belongs to exactly one team. Inside a sheet a problem appears once, and each position (1, 2, 3 …) is used once.
  7. Values that can be computed (difficulty band, solved count, rank, sheet progress) are never stored; they are computed by views.

3.3. Relational Schema

The ER diagram is converted to tables with the standard mapping rules:

  • Strong entity → a table with the entity's key as primary key (University, User, Team, Problem, Topic, Sheet).
  • Weak entity → a table whose primary key is the owners' keys plus the partial key: Submission(user_id, problem_code, submitted_at).
  • 1 : N relationship → the key of the "1" side is added as a foreign key on the "N" side (studies_at → User.univ_id, member_of → User.team_id, assigned_to → Sheet.team_id). Partial participation of the N side gives a nullable foreign key (User.team_id).
  • M : N relationship → a separate junction table whose key is both keys, plus any relationship attribute (tagged → Problem_Topic, contains → Sheet_Problem with position).
  • Derived attribute → not stored; computed in a view (§3.5).

Primary keys are underlined; → marks a foreign key and the table it references.

Every PRIMARY KEY and UNIQUE constraint creates a B-tree index automatically. 3.4.2 First Normal Form (1NF)

Definition: a relation is in 1NF if every attribute holds a single atomic value (no lists, no repeating groups). The topics column violates this.

Fix: a multi-valued attribute is moved to its own relation together with the key of the thing it describes. Topics describe a problem, so we create Problem_Topic(problem_code, topic) with one row per (problem, topic) pair — 1547G now gives two rows, (1547G, DP) and (1547G, Graphs). Later, topic names are moved to a Topic(topic_id, topic_name) lookup table so a name is typed once (renaming "DP" to "Dynamic Programming" becomes a one-row update).

What remains is the 1NF relation we analyse in the rest of this section:

PRACTICE_LOG(user_id, name, email, univ_id, univ_name, team_id, team_name, problem_code, title, rating, submitted_at, verdict, language)

3.4.3 Functional dependencies

Definition: X → Y (X functionally determines Y) if any two tuples that agree on X must also agree on Y. An FD is trivial if Y ⊆ X (e.g. UM → U), otherwise non-trivial. From the business rules, the spreadsheet's notes give this set F (written exactly as collected, including some redundancy that §3.4.6 removes):

#FDReason
F1U → N M I Ga user has one name, e-mail, university, team
F2M → Ue-mail is unique
F3I → Ja university id has one name
F4G → Ka team id has one name
F5P → T Ra problem has one title and rating
F6U P S → V Lone user, one problem, one instant ⇒ one submission
F7U M → Nnoted separately on the sheet
F8U → J"the student's university name"
F9U P S → T"each submission row shows the problem title"

Armstrong's axioms are the rules for deriving new FDs from F:

  • Reflexivity: if Y ⊆ X then X → Y.  (UP → P)
  • Augmentation: if X → Y then XZ → YZ.  (P → T gives PS → TS)
  • Transitivity: if X → Y and Y → Z then X → Z.  (U → I, I → J gives U → J)
  • Derived rules: union (X → Y, X → Z ⇒ X → YZ), decomposition (X → YZ ⇒ X → Y), pseudo-transitivity (X → Y, WY → Z ⇒ WX → Z).

3.4.4 Attribute closure and candidate keys

Definition: the closure X+ is the set of all attributes that X determines. Algorithm: start with result = X; repeatedly, for every FD A → B in F with A ⊆ result, add B to result; stop when nothing changes. X is a super key if X+ contains every attribute, and a candidate key if, in addition, no proper subset of X is a super key.

{U, P, S}+

start : {U, P, S}

F1 U → NMIG : {U, P, S, N, M, I, G}

F3 I → J : {U, P, S, N, M, I, G, J}

F4 G → K : {U, P, S, N, M, I, G, J, K}

F5 P → TR : {U, P, S, N, M, I, G, J, K, T, R}

F6 UPS → VL : {U, P, S, N, M, I, G, J, K, T, R, V, L} = all 13 attributes ✓ super key

{M, P, S}+

start {M, P, S} → F2 M → U adds U → now {U, P, S} ⊆ result, so (as above) all 13 attributes ✓ super key

Are they minimal?

XX+Super key?
{U}{U, N, M, I, G, J, K}no
{M}{M, U, N, I, G, J, K}no
{U, P}{U, P, N, M, I, G, J, K, T, R}no — missing S, V, L
{U, S}{U, S, N, M, I, G, J, K}no
{P, S}{P, S, T, R}no

A quick way to see this: P and S never appear on the right-hand side of any FD, so they must be in every key. {P, S} alone is not enough, and adding either U or M completes it. Hence the candidate keys are {U, P, S} and {M, P, S}. We choose {U, P, S} as the primary key.

  • Prime attributes (in some candidate key): U, M, P, S.
  • Non-prime attributes: N, I, J, G, K, T, R, V, L.

3.4.5 Closure of a set of FDs (F+)

Definition: F+ is the set of all FDs that can be derived from F using Armstrong's axioms. It is far too large to list (it includes every trivial FD over 13 attributes), so in practice we use two techniques:

(a) Deriving members of F+ with the axioms:

Derived FDDerivation
U → JU → I (F1, decomposition), I → J (F3) ⇒ transitivity
M → NM → U (F2), U → N (F1, decomposition) ⇒ transitivity
M → KM → U, U → G, G → K ⇒ transitivity twice
U P → TP → T (F5) ⇒ augmentation with U gives UP → TU ⇒ decomposition
M P S → V LM → U (F2) and UPS → VL (F6) ⇒ pseudo-transitivity

(b) Membership test using attribute closure: X → Y is in F+ exactly when Y ⊆ X+.

Is … in F+?ComputeAnswer
M → K{M}+ = {M,U,N,I,G,J,K} ∋ KYes
I → U{I}+ = {I, J} ∌ UNo — many students share a university
G → I{G}+ = {G, K} ∌ INo — the data does not force a team's university

Two FD sets F and G are equivalent (F+ = G+) if every FD of G is in F+ and every FD of F is in G+; this is how we check that the minimal cover below says the same thing as F.

3.4.6 Minimal (canonical) cover

Definition: a minimal cover Fc is an FD set equivalent to F in which (1) every right-hand side is a single attribute, (2) no left-hand side has an extraneous attribute, and (3) no FD is redundant.

Step 1 — single attribute on the right. Splitting F gives 14 FDs:

U→N, U→M, U→I, U→G, M→U, I→J, G→K, P→T, P→R, UPS→V, UPS→L, UM→N, U→J, UPS→T

Step 2 — remove extraneous left-hand attributes. In XA → B, A is extraneous if B ∈ X+ (computed with F).

FDTry removingClosureResult
UM → NM{U}+ ∋ NM extraneous → U → N (already present, drop)
UPS → TU, then S{PS}+ ∋ T, then {P}+ ∋ T→ P → T (already present, drop)
UPS → VU / P / S{PS}+, {US}+, {UP}+ — none contain Vnothing extraneous
UPS → LU / P / Ssame, none contain Lnothing extraneous

In UM → N, U is also extraneous on its own (M → N holds via M → U → N). Removing U first instead of M would end with M → N in place of U → N. Both answers are correct: a minimal cover is not unique. We keep U → N because it reads naturally.

Step 3 — remove redundant FDs. A → B is redundant if B ∈ A+ computed without that FD.

Minimal cover (written with the union rule for readability):

Fc = { U → N M I G,  M → U,  I → J,  G → K,  P → T R,  U P S → V L }

Equivalence check: every FD of Fc is in F, and the three removed FDs (UM → N, U → J, UPS → T) were each shown above to follow from the rest, so Fc+ = F+.

3.4.7 Second Normal Form (2NF)

Definition: a relation is in 2NF if it is in 1NF and no non-prime attribute is partially dependent on a candidate key (i.e. depends on only part of a composite key).

PRACTICE_LOG has key {U, P, S}. Checking Fc:

FDAnalysis2NF?
U → N M I GU is a proper part of the key; N, I, G are non-primeViolation (partial)
P → T RP is a proper part of the key; T, R non-primeViolation (partial)
M → UU is prime, so this does not violate 2NFOK
U P S → V Lfull dependency on the whole keyOK

Decomposition: for each partial dependency X → Y, take out X+ as its own relation.

R1 = USER_INFO(U, N, M, I, J, G, K)   ← {U}+

R2 = PROBLEM(P, T, R)   ← {P}+

R3 = SUBMISSION(U, P, S, V, L)   ← key + what depends on the whole key

R1 and R2 have single-attribute keys, so they cannot have partial dependencies; in R3, V and L depend on the whole key. All three are in 2NF. The insertion anomaly for problems is gone: a problem can now exist with no submissions.

3.4.8 Third Normal Form (3NF)

Definition: a relation is in 3NF if for every non-trivial FD X → A, either X is a super key or A is a prime attribute. Equivalently: it is in 2NF and no non-prime attribute is transitively dependent on a key.

R1 = USER_INFO(U, N, M, I, J, G, K) violates 3NF: I → J and G → K hold, but neither I nor G is a super key and J, K are non-prime. These are transitive dependencies U → I → J and U → G → K — the source of the "rename the university in every row" update anomaly.

Decomposition of R1:

R1a = USER(U, N, M, I, G)   FDs: U → NMIG, M → U

R1b = UNIVERSITY(I, J)   FDs: I → J

R1c = TEAM(G, K)   FDs: G → K

Now every determinant in every relation is a key: in USER, U and M are both candidate keys; in UNIVERSITY, TEAM, PROBLEM and SUBMISSION the only determinant is the primary key. All relations are in 3NF.

Cross-check with the 3NF synthesis algorithm

The textbook synthesis algorithm builds one relation per FD of Fc — (U,N,M,I,G), (M,U), (I,J), (G,K), (P,T,R), (U,P,S,V,L) — drops (M,U) because it is contained in (U,N,M,I,G), and adds a key relation only if no relation already contains a candidate key ((U,P,S) is inside SUBMISSION, so none is added). The result is exactly the decomposition above. Synthesis is guaranteed to be lossless and dependency preserving; §3.4.10 and §3.4.11 prove both directly.

3.4.9 BCNF check (beyond 3NF)

BCNF is stricter: for every non-trivial X → A, X must be a super key (no exception for prime A). Every determinant in our decomposition is a candidate key, so all relations are also in BCNF.

3.4.10 Lossless-join decomposition

Definition: decomposing R into R1 … Rn is lossless if joining the pieces always gives back exactly R — no tuples lost and, more importantly, no spurious tuples added.

Binary test: R → {R1, R2} is lossless if R1 ∩ R2 → R1 or R1 ∩ R2 → R2 is in F+ (the common attributes form a key of one side). Every split we made passes it:

SplitR1 ∩ R2Test

(U,P,S,T,R,V,L) → PROBLEM + SUBMISSION{P}P → PROBLEM ✓
USER_INFO → (U,N,M,I,G,K) + UNIVERSITY{I}I → UNIVERSITY ✓
(U,N,M,I,G,K) → USER + TEAM{G}G → TEAM ✓

Apply the FDs: whenever two rows agree on the left side of an FD, make their right-side values equal (prefer a). If some row becomes all a, the decomposition is lossless.

3.4.11 Dependency preservation

Definition: a decomposition R1 … Rn is dependency preserving if (F1 ∪ F2 ∪ … ∪ Fn)+ = F+, where Fi is the projection of F+ onto Ri (the FDs that use only attributes of Ri). If it holds, every constraint can be checked inside a single table, without joins.

RelationProjected FDs FiFDs of Fc covered
USER(U,N,M,I,G)U → NMIG, M → UU → NMIG, M → U
UNIVERSITY(I,J)I → JI → J
TEAM(G,K)G → KG → K
PROBLEM(P,T,R)P → TRP → TR
SUBMISSION(U,P,S,V,L)UPS → VLUPS → VL

Each FD of Fc lies completely inside one relation, so the union of the projections is Fc itself, whose closure equals F+. The decomposition is dependency preserving. ✓

Counter-example: a decomposition that loses a dependency

Suppose USER_INFO(U, N, M, I, J, G, K) had been split into X(U, N, M, I, G, K) and Y(U, J) (the university name stored against each user). It is lossless (U is a key of both), but I → J is no longer inside any single table. Testing it with the preservation algorithm:

result = {I}

on X: ({I} ∩ X)+ ∩ X = {I, J} ∩ X = {I} → no change

on Y: ({I} ∩ Y)+ ∩ Y = ∅ → no change

J ∉ result ⇒ I → J is not preserved

The database could then store two different names for the same univ_id and nothing would stop it short of joining X and Y on every insert. Our chosen decomposition avoids this.

Design decision worth noting: a problem's URL and difficulty band are functions of problem_code and rating; storing them would add the FDs problem_code → url and rating → difficulty, the second of which is a transitive dependency. They are therefore derived, not stored. The Codeforces rating, by contrast, is stored (cf_rating, cf_max_rating): it cannot be computed from our tables, because it comes from Codeforces' own contest history. It is a snapshot refreshed on every sync, and depends only on user_id, so User stays in BCNF.
